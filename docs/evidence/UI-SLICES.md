## How it was built and checked

- Per slice: tests first for the pure parts (they are in `agent-core`, so the existing CI task runs them), then the UI, then `./ci.sh tests` and `./ci.sh build` in the owner's instabox sandbox (Debian 13, 4 vCPU, 7 GB RAM, JDK 17, Android platform 36), which run the same Gradle tasks as `.github/workflows/ci.yml` for tests and APKs plus the manifest, network-use and hard-coded-string checks. The `:eval:gate` task was run on the pre-UI code only (no eval code changed).
- **Measured** ("all declared tests ran" class counts): 109 before the UI work, 111 after slice 1, 112 after slice 2, 113 after slice 3, 116 after slices 4 to 7. Build and checks passed at each step on the final commit of that step.
- The sandbox build also caught real mistakes: slice 1 and slices 4 to 6 each failed the hard-coded-string check once (fixed), two unescaped apostrophes in new strings were noticed by the author before that build (fixed), and a syntax check of the phone driver found a line my edit script had mangled (fixed in `212f74e`).
- The owner's computer ran only git, `adb install` and a screenshot or two. The rule is in memory: no tests, builds or phone scripts on the owner's computer unless asked (a runaway case runner froze it on 2026-11-04).
- APK delivery from the sandbox: copy the APK to `~/out`, serve it with `python3 -m http.server 8080`, publish port 8080 on the instabox Ports tab, `curl` it, compare the SHA-256, unpublish the port and stop the server. The owner approved each publish separately. The sandbox build is signed with the owner's standard Android debug keystore (copied into the sandbox with the owner's approval, because a differently signed debug build cannot update the installed one). It is a debug key only; no release key is in the sandbox.

## Rulings made while building (for the review)

1. **Owner decisions taken from Fable's recommendations** (the owner answered "yes" to starting slice 1 and "all fine for now" after slice 2, without choosing among them): Recent activity leaves the home screen (done cards stay in the thread, the full list is Settings, History); newest turn at the bottom; "Namaste" only in the empty-thread greeting; the fixed palette.
2. **The palette lives in `agent-core`** as plain 0xRRGGBB data, so `ColorContrastTest` runs under the existing `:agent-core:test` CI task. The alternative was a new `:app:testDebugUnitTest` CI task with new test dependencies in the verification file. The app maps the data to Compose colours. Cost: a little UI data in a core module.
3. **Icons are simple shapes drawn by hand** (alarm, task, note, calendar, chat, route, plan, info, help, warning, history, flag, lock, expand, volume) plus a few that follow the common Material outlines from memory (settings gear, call, mic, send, back, check). None was compared with the Material Symbols files, and none has been seen on a screen. The `material-icons-extended` dependency was not added.
4. **A clarifying question is recognised by a trailing "?"** (`NoticeKind.of`), not by a stored flag, to avoid a schema change. Cost: a refusal that happens to end in a question mark would get the question icon.
5. **Chat label kept**: the existing string "Bheem, from the model, may be wrong" now sits next to the sparkle inside the outlined bubble instead of the design's "From the model, may be wrong", so the phone driver and the documented wording stay valid.
6. **Plan step numbers** are in the card title ("1. Reminder"); no separate numbered badge.
7. **No new action type, permission or network call** was added, so `docs/SECURITY.md` is unchanged.
